# ADR-002: Event Pipeline — Kafka for Async Ingestion + DB-Level Deduplication

**Status:** Accepted  
**Date:** 2026-05-16

## Context

Events (exposure + conversion) are generated by the SDK in the demo app and sent to the backend.
Requirements:
- Absorb burst traffic from k6 without blocking the HTTP handler
- Reliable buffer between ingestion and storage
- Deduplication on SDK retries or consumer replay
- Ability to add a second consumer without changing the SDK (real-time alerting, export)

## Decision

**Kafka** as an async event bus between the HTTP handler and the PostgreSQL writer.  
**Deduplication:** idempotent insert via `event_id` UUID at the DB level.

```
SDK
  │ POST /sdk/events (batch, max 500)
  ▼
Backend Handler
  │ validate + produce (async, fire-and-forget)
  ▼
Kafka topic: ab.events.raw
  │ consume (500 msgs OR 500ms, whichever first)
  ▼
Events Consumer (goroutine in the same backend process)
  │ bulk INSERT ... ON CONFLICT (event_id) DO NOTHING
  ▼
PostgreSQL events table
```

## Kafka Setup

**Broker:** Kafka 3.7 in KRaft mode (no Zookeeper).  
**Go client:** `github.com/segmentio/kafka-go` — pure Go, clean API.

### Topic Design

| Topic | Partitions | Key | Retention |
|---|---|---|---|
| `ab.events.raw` | 3 | `experiment_id` | 7 days |
| `ab.events.dlq` | 1 | — | 30 days |

**Why key = `experiment_id`:**
- Events for the same experiment go to the same partition → ordering within an experiment
- Consumer can process different partitions in parallel

**DLQ (Dead Letter Queue):**
If an insert fails after N retries (poison pill) → produce to `ab.events.dlq`.
An operator can inspect and replay manually.

### Producer (in the HTTP handler)

```go
// Async, non-blocking — HTTP handler does not wait for Kafka ack
func (h *EventHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    batch := parseBody(r)
    if err := validate(batch); err != nil {
        writeError(w, 400, err)
        return
    }

    for _, evt := range batch {
        msg := encodeEvent(evt)           // JSON or protobuf
        h.producer.WriteMessages(r.Context(), kafka.Message{
            Key:   []byte(evt.ExperimentID),
            Value: msg,
        })
    }

    w.WriteHeader(http.StatusAccepted)   // 202, not 200: accepted by Kafka, not yet in DB
}
```

**202 Accepted** is semantically important: data has been accepted but is not yet persisted in PG.
The SDK is fine with this — it never reads back its own events.

### Consumer (goroutine in the same process)

```go
func (c *EventConsumer) Run(ctx context.Context) {
    reader := kafka.NewReader(kafka.ReaderConfig{
        Brokers:  c.brokers,
        Topic:    "ab.events.raw",
        GroupID:  "events-writer",
        MinBytes: 10e3,                  // 10KB
        MaxBytes: 10e6,                  // 10MB
        MaxWait:  500 * time.Millisecond,
    })

    batch := make([]Event, 0, 500)
    for {
        msg, err := reader.FetchMessage(ctx)
        if err != nil { break }

        batch = append(batch, decodeEvent(msg.Value))

        if len(batch) >= 500 {
            c.flushBatch(ctx, batch, reader)
            batch = batch[:0]
        }
    }
}

func (c *EventConsumer) flushBatch(ctx context.Context, batch []Event, reader *kafka.Reader) {
    if err := c.repo.BulkInsert(ctx, batch); err != nil {
        c.sendToDLQ(batch)
    }
    reader.CommitMessages(ctx, ...)   // commit only after successful insert
}
```

**Commit after write** — at-least-once semantics.  
If the process crashes after insert but before commit → events are re-consumed → `ON CONFLICT DO NOTHING` prevents duplicates.

## Deduplication

```
SDK generates event_id = uuid.New() when the event is created (once).
On retry → same event_id in a new HTTP request → new Kafka message → re-insert → ON CONFLICT DO NOTHING.

SQL:
  INSERT INTO events (id, project_id, user_id, experiment_id, variant_id, event_type, ts)
  VALUES ($1, $2, $3, $4, $5, $6, $7)
  ON CONFLICT (id) DO NOTHING
```

This covers all failure scenarios:
- SDK HTTP retry (network timeout)
- Kafka consumer reprocessing after a crash
- Duplicate messages in Kafka (at-least-once delivery)

## Trade-offs

**Added complexity:**
- Consumer goroutine requires graceful shutdown
- 202 instead of 200 — SDK must handle this
- Local dev requires a running Kafka instance

**Benefits:**
- HTTP handler responds in <1ms regardless of PG load
- k6 burst traffic is buffered in Kafka; PG writes at its own pace
- DLQ provides visibility into problematic events
- Replay: if analytics reveals a processing bug → events can be replayed from the beginning
- Production-like approach → valuable for the thesis and for real-world experience

## Consequences

- `POST /sdk/events` returns **202 Accepted** (not 200)
- Backend requires graceful shutdown: flush the consumer first, then close
- Integration tests require testcontainers-go (Kafka container in tests) or a mock
- If Kafka is unavailable at startup — the backend must not crash: retry with exponential backoff
